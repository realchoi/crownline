# 阶段 4B · 结构化历史关系设计

## 背景与目标

Crownline 的阶段 4A 已支持选择两个真实政权，计算无公元 0 年、闭区间口径下的存续时间交集，并并列展示双方基本信息和共同期统治者。数据契约 v3 已预先定义 `Relationship`、`HistoricalEvent`、`Source`，生成器也会把与实体相关的关系、事件和来源收进该实体的详情分片，但当前生产数据中的关系与事件仍为空，对比台也尚未消费这些字段。

阶段 4B 在现有时间对比之上增加有来源支持、人工校订的政权间历史关系。页面必须把自动计算的时间重叠与人工校订的战争、联盟、外交等关系明确分层；没有匹配记录时只说明“暂无已校订关系数据”，不得推断双方没有历史关系。

## 范围

本阶段包含：

- 从双方现有详情分片中选择、合并和去重同时涉及两个当前政权的关系；
- 支持战争、联盟、外交、朝贡、臣属、贸易、文化交流七种既有关系类型；
- 按关系类型分组展示有效区间、参与角色、摘要、可信度、争议说明、相关事件和来源；
- 为七种类型各录入至少一条可追溯的代表性生产数据；
- 为少量关键关系挂接战役、条约或外交事件，不建设完整事件知识图谱；
- 对单条无法安全展示的关系进行隔离，不让它破坏时间对比、统治者或其他有效关系；
- 更新路线图、数据契约说明和面向用户的功能说明。

本阶段不包含：

- 自动推断接壤、疆域接触或空间重叠；
- 完整覆盖任意政权组合的历史关系；
- 完整事件知识图谱、事件详情页或事件检索；
- 修改 URL 对比选择协议；
- 新增依赖、数据库、远程 API 或后台服务；
- 重构与阶段 4B 无关的详情加载、时间轴或地图能力。

## 方案选择

### 采用：复用实体详情分片

双方详情分片已经包含与各自相关的 `relationships`、其引用的 `events`，以及这些记录需要的 `sources`。对比台继续使用阶段 4A 的两个详情请求，在领域层合并双方候选数据并按关系 ID 去重，不引入新的网络端点或索引字段。

该方案沿用现有懒加载与引用闭包，改动边界最小。关系生产数据仍保存在集中数据源中，由生成器复制到适用实体详情；页面不关心数据源的物理文件划分。

### 未采用：按政权对生成独立关系分片

独立关系分片能进一步隔离统治者详情和关系详情，但需要新增索引、文件命名、生成、加载与缓存协议。当前数据量和加载场景不足以抵消复杂度，因此留待关系规模明显增长后再评估。

### 未采用：把关系放入首屏索引

首屏索引方案实现直接，但会让所有关系、事件和来源随首页加载，违背现有详情懒加载边界，也会随着史料扩充持续放大首屏数据。

## 领域设计

新增独立的历史关系选择模块，接收两个实体 ID 和双方详情中的未知候选记录，返回可直接展示的结构：

- `groups`：按固定类型顺序排列的有效关系组；
- `omittedCount`：因结构、配对、重复冲突或引用闭包问题而无法安全展示的候选数；
- 每条有效关系附带已解析的参与方、事件和来源，不让 React 组件自行拼接引用。

候选关系必须满足以下条件才可展示：

1. 记录为对象，具有非空且稳定的 `id`；
2. `type` 属于七种已支持类型；
3. `participants` 至少包含两个不重复实体，并同时包含当前两个政权；
4. `periods` 为合法、正序且不含公元 0 年的区间数组；
5. `summary` 非空；
6. `confidence` 属于现有可信度枚举，`low` 或 `disputed` 带非空说明；
7. 至少存在一条可解析来源引用；全部来源引用均能在双方来源并集中找到；
8. 每个 `eventId` 均能在双方事件并集中找到，事件本身具有可展示的标题、区间和摘要。

双方详情中同 ID、内容一致的关系只展示一次。同 ID 但内容冲突的候选不选择任意一份，而是整条隔离并计入一次省略。类型组按产品定义顺序排列；组内关系按最早起始年、最早结束年、ID 稳定排序。

关系是否展示只由结构化记录及当前两个参与方决定，不要求关系区间与双方的共同存续区间再次相交。这样可以保留使臣往来、条约余波或政权存续边界存在口径差异的人工校订记录；若具体数据存在这类情况，摘要或可信度说明必须披露采用口径。

## 数据流

```text
URL 中的两个 compare ID
        │
        ▼
阶段 4A 加载双方实体详情
        │
        ├── 人物、任期 ──► 共同期统治者
        │
        └── 关系、事件、来源
                │
                ▼
       合并候选、逐条校验、按 ID 去重
                │
                ├── 有效关系 ──► 类型分组与关系卡片
                └── 无效关系 ──► omittedCount 提示
```

领域模块只消费已加载详情，不发起请求。`ComparisonPanel` 继续负责请求生命周期、重试和切换政权后的迟到结果保护。

## 界面设计

对比台保留阶段 4A 的时间摘要和双方档案，在两列政权信息之后增加独立的“已校订历史关系”区块。标题和辅助文案明确区分：

- 上方“时间关系”由存在区间自动计算；
- 下方“历史关系”来自人工校订并附来源。

有关系时：

- 顶部显示匹配到的关系条数和覆盖类型数；
- 每个非空类型形成一个分组，使用中文类型名称；
- 关系卡展示区间、双方角色、摘要和可信度标签；
- `confidenceNote` 作为“口径与争议”说明展示；
- 相关事件使用紧凑列表展示标题、区间和摘要；
- 来源使用可展开列表展示完整 citation、locator/note，并在有 URL 时提供新标签页链接。

无关系时显示：“暂无已校订关系数据。这表示当前数据集尚未收录，不代表双方历史上没有关系。”

存在坏记录时，在有效结果下方或空状态中显示非阻断提示：“有 N 条关系数据格式异常，已跳过。”不向用户暴露堆栈或内部字段路径。

加载关系不新增独立转圈状态，因为它与阶段 4A 的详情同批返回。双方详情尚未就绪时保留现有加载提示；详情请求整体失败时保留现有重试行为。

桌面端关系区块采用单列纵向阅读，避免在已经双列的政权档案下继续压缩长摘要与来源；移动端保持同一信息顺序。颜色沿用现有 `--accent`、`--period`、`--muted` 和表面变量，可信度不能只靠颜色表达。

## 容错边界

生产数据在构建前仍必须通过 JSON Schema 与全量语义校验，错误数据不能被静默发布。浏览器侧的逐条容错是第二道防线，用于处理缓存损坏、版本漂移或局部传输数据异常，不替代构建期校验。

运行时详情校验继续保护实体 ID、人物、任期和来源等核心结构。关系选择模块把 `relationships` 视为不可信边界并逐条收窄；单条关系或其专属事件无法解析时只影响该关系。详情根对象、双方实体详情、人物任期等核心数据无法加载时，仍使用现有面板级错误和重试，因为这已超出“单条坏关系”的容错范围。

## 首批数据策略

首批生产数据以“小而可核查”为原则：七种关系类型各至少一条，优先选择当前数据集中双方实体都已存在、时间范围与史料定性较清晰的案例。允许同一对政权存在多种关系，例如先结盟后战争，但每条记录只表达一个清晰关系概念。

史料选择优先级为学术出版物、博物馆、档案馆、大学、国际组织或其他权威机构资料；只有在缺少合适机构页面时才使用高质量通识二手来源，并通过第二来源交叉核对。每条关系至少引用一个直接支持其关系类型、参与方和时间范围的来源，争议性定性需使用 `low` 或 `disputed` 并说明口径。来源页面的访问日期统一记录为实际校订日期。

少量事件只用于提升关系可读性，首批优先挂接能够代表关系转折点的战役、条约或外交事件。关系摘要不能仅复述事件标题，事件也不能成为关系来源追溯的唯一替代。

## 测试与验收

领域测试覆盖：

- 只返回同时包含当前两个政权的关系；
- 双方详情重复记录去重；
- 七类中文标签、分组顺序与组内年代排序；
- 参与角色、来源引用和相关事件正确解析；
- 同 ID 内容冲突、未知类型、坏区间、缺失来源、悬空事件、争议说明缺失逐条隔离；
- 一条坏记录与一条好记录并存时，好记录仍可展示且 `omittedCount` 正确。

页面测试覆盖：

- 时间关系与历史关系独立呈现；
- 有记录时展示类型、摘要、事件、可信度、争议说明和来源链接；
- 无记录时使用“暂无已校订”口径；
- 坏记录只产生非阻断提示；
- 既有详情加载失败重试、迟到请求保护和统治者展示不回归。

数据测试覆盖：

- 七种关系类型在生产数据中均至少出现一次；
- 每条关系双方、区间、来源和可信度满足契约；
- 关系引用的事件与来源闭合；
- 每个首批案例能通过直接来源追溯。

最终验证运行数据生成与校验、完整测试、TypeScript 静态检查、生产构建、字体字符检查和 `git diff --check`。验收结果必须同时满足：每条展示关系可追溯、时间与人工关系分层、无数据不作历史否定、单条坏关系不导致整个对比页面失效。
